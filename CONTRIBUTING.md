# Contributing to Charland

Thank you for helping. Charland is free and open source, and pull requests are how it gets better.

## The short version

1. Fork, make a branch, build (see below), change something, make sure `swift test` passes in both packages.
2. Open a pull request that says what it does and, for anything visible, shows a screenshot or a short recording.
3. One focused change per pull request is easier to review than ten.

By contributing you agree that your contribution is licensed under GPL-3.0-or-later like the rest of the project.
You keep the copyright on your work.

## The rule that matters most: know where code comes from

Charland is GPL-3.0-or-later and already contains credited code adapted from Vorssaint, which has the same license
(see `THIRD_PARTY_LICENSES.md`). So:

- Code under **GPL-3.0-or-later** (or a compatible license: MIT, BSD, Apache-2.0) may be adapted, **with a credit**: say
  in the file and in the pull request where it comes from, keep its copyright line, and add it to
  `THIRD_PARTY_LICENSES.md` and `Sources/Charland/Resources/Terze parti.txt`.
- Code under a license that is **not** compatible (GPL-2.0-only, proprietary, "source available", no license at all) or
  whose license you have not checked must not be copied, translated or "rewritten from memory". Look at it to
  understand a behavior, then write your own.
- Do not paste in code produced by a tool from such sources.
- Assets (images, icons, sounds, fonts) and trademarks follow the same rule; the Apple, Anthropic and OpenAI logos and
  artwork are not ours to ship.

## Building

Requirements: Apple silicon Mac, macOS 26+, Xcode 27, `brew install xcodegen`.

```bash
cp Config/Local.xcconfig.example Config/Local.xcconfig
Scripts/scarica-dipendenze.sh
Scripts/build.sh
```

`Scripts/scarica-dipendenze.sh` downloads the pinned sherpa-onnx release (the SHA-256 is checked) and builds it with
Charland's small patch (`Scripts/sherpa-onnx-charland.patch`, explained in `THIRD_PARTY_LICENSES.md`).
`Scripts/build.sh` generates the Xcode project from `project.yml` (it is not committed), so edit `project.yml`, not
the `.xcodeproj`. Build products go to `~/Library/Caches/charland-build`; set `CHARLAND_BUILD_DIR` to change that.

### Signing

macOS ties the permissions you grant (Accessibility, Microphone, Calendar...) to the app's signature.

- **Ad hoc** (the default in `Local.xcconfig.example`): needs no Apple account, but macOS asks for the permissions
  again after every build.
- **Your own Apple Development certificate**: set `CHARLAND_TEAM` and, if you like, `CHARLAND_BUNDLE_ID` in
  `Config/Local.xcconfig`, remove the ad hoc lines, run `Scripts/genera-identita.sh && xcodegen`. Permissions then
  survive rebuilds. Use your own bundle id if you also run the official Charland. It separates the app identity and the preferences, but not everything: the API socket folder (`~/Library/Application Support/Charland`), the helper label and the `charland` command's shell folder keep the same names, and `Scripts/build.sh install` always replaces `/Applications/Charland.app`. Do not run `install` on a Mac where you use the official app.

If you distribute a fork, also change where it sends bug reports and ideas (`SupportLinks` in
`Sources/Charland/Settings/SupportPane.swift`): by default they go to Char Studio.

`Config/Identita.xcconfig` is the single place for the app's name, bundle id, command name and URL scheme.

Known limitation: the closed-lid keep-awake helper (`CharlandHelper`) only talks to an app signed by the official
team (`Sources/Shared/HelperProtocol.swift`). In your own builds Charland still offers to register the helper, but it
will refuse to talk to your app: change that requirement to match your bundle id and team to use the feature.

`Packages/CharlandCore/Sources/CharlandCore/Identity.generated.swift` is generated by `Scripts/genera-identita.sh` from
your `Config/Local.xcconfig`. If you override the bundle id, do not commit that file
(`git update-index --skip-worktree` on it).

Development builds never check for updates and do not even create the updater. Only official builds (compiled with
`CHARLAND_OFFICIAL`, made by the maintainer) do.

## Layout

| Path | What |
|---|---|
| `Sources/Charland` | the app: `Island`, `Dock`, `Voice`, `Agents`, `LockScreen`, `Search`, `Ruler`, `Wallpaper`, `Settings`... |
| `Sources/CharlandHelper` | the privileged helper (closed-lid keep-awake) |
| `Sources/NowPlaying` | the "Now Playing" reader that runs inside `/usr/bin/perl` |
| `Sources/VoiceEngine` | the speech engine, in its own XPC process |
| `Sources/charland-cli` | the `charland` command |
| `Packages/CharlandCore` | pure logic with tests: island state machine, motion, dictation rules, activities |
| `Packages/CharlandKit` | the public client of the API ([docs/API.md](docs/API.md)) |
| `Scripts` | build and dependency scripts |
| `docs` | the API, plus notes on dictation and a speech engine comparison (Italian) |

Put logic that can be tested without a screen in `CharlandCore`, with tests. Keep views thin.

## Testing

- `swift test` in `Packages/CharlandCore` and `Packages/CharlandKit`.
- `Charland --selftest` runs the island's motion checks headless.
- `Charland --demo <scene>`, `--snapshot <folder>`, `--dock`, `--appunti`, `--ricerca`, `--blocco` open single parts of
  the app for manual checks.

## Private macOS APIs

The lock screen, the Spaces handling, the Dock tracking and "Now Playing" use private APIs (SkyLight/CGS, MediaRemote,
`dlsym`). They are fine outside the App Store and break from time to time on new macOS releases. If you touch them,
resolve symbols at runtime, fail soft, and say in the pull request which macOS version you tried.

## Language

The first versions were written in Italian: many code comments, `docs/*.it.md` and a few file and script names
(`scarica-dipendenze`, `genera-identita`) are Italian. Issues, pull requests, new comments and new docs
in English are welcome and preferred; translating old comments is a nice first contribution.

## Style

Swift 6 with strict concurrency, SwiftUI first, AppKit where SwiftUI cannot do it. Follow the surrounding code.
Nested corners are concentric (inner radius = outer radius minus the distance between them). No pulsing dots, no
decorative "AI" gradients: the look is plain, black glass and clear type.

## Reporting bugs and ideas

Use the issue templates. For anything about security, read [SECURITY.md](SECURITY.md) and do not open a public issue.
